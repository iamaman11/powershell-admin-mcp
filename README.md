# WindowsAdminMCP — native Windows administration

Canonical source: [iamaman11/powershell-admin-mcp](https://github.com/iamaman11/powershell-admin-mcp).

**Start here:** [22 typed tools and everyday tasks](docs/QUICKSTART.md).
Candidate native MCP 0.8.1-dev; .NET 10 LTS (current runtime 10.0.15, build SDK 10.0.404); MCP SDK 2.4.0; official OpenAI tunnel-client 0.0.21; SQLite schema 4. The installed commit and version must be read back from the actual service. CI success is not remote acceptance. All NuGet dependencies are pinned centrally in `Directory.Packages.props` and in **four tracked `packages.lock.json` project graphs**, with an exact `global.json` SDK and a single generated tunnel vendor lock. See [dependency inventory and update rules](docs/DEPENDENCIES.md). The newer .NET 11 STS major is not an automatic upgrade from the supported .NET 10 LTS branch.

## Architecture and execution context

One Windows service (SYSTEM) owns the durable SQLite queue, state transitions, encrypted job data and concurrent system execution. One interactive elevated supervisor owns one USER worker and **one or more independent official OpenAI Tunnel processes**; each tunnel starts its own stateless MCP stdio child, and all children use the existing authenticated local service pipe. The service derives the SID, logon SID and session from Windows rather than accepting arbitrary user IDs. No duplicate SYSTEM service, SQLite store, logon task or automatic user impersonation for execution.

### Legacy test-generation cleanup (#56)

The previously approved generation of 17 `NEEDS_RECONCILIATION` jobs can be
retired **once** through `powershell_update(action=FORGET_LEGACY,
expected_commit=<installed exact commit>)`. This uses the existing verified
interactive Scheduler operator: it requires an accepted package, no active jobs
and exactly the old 17 entries, drains ingress, stops SCM, runs an offline
fingerprint-checked SQLite transaction, verifies no unrelated data changed and
restarts. `powershell_update(STATUS)` returns the typed action, deleted count
and outcome. It never executes, reconciles or replays those old commands.
Failing preconditions means no deletion; ambiguous outcomes require read-only
status/doctor before any other action. Do not use `powershell_job(prune)` to
pretend those unknown jobs were removed. This is intentionally not a general
purpose job-deletion API. See `docs/ARCHITECTURE.md` and Issue #56.

`powershell_exec` and `powershell_job submit` default to USER for non-SYSTEM clients; explicitly set execution_context=SYSTEM for service operations. USER uses the existing administrator profile, HKCU, environment and user network/application permissions. Unavailable matching runner returns USER_CONTEXT_UNAVAILABLE; never silently switch to SYSTEM. A persisted USER job stays bound to its original logon/sid/session; after logoff a different logon cannot claim/resume it. Old queued USER work can be cancelled; interrupted work needs reconciliation. Reboot checkpoints require explicit SYSTEM. Local admins are trusted administrators, not a security sandbox; physical multi-user fairness and session transitions still require acceptance.

INTERNET owns networking. Tunnel startup intentionally requires the current supported INTERNET deployment: adapter internet-tun Up and exactly one running C:\internet\sing-box.exe. The app reads these prerequisites and does not change routes or start INTERNET. RDP, locked or non-console desktops do not capture the physical desktop; typed failure explains the check. WSL, Docker, browser and mapped drive support depends on the actual caller's profile and privileges; the CLI's presence is not proof that a daemon or distribution is running.

## One operator entry point

Run locally in elevated PowerShell 7 (Windows x64) from the authorized interactive logon:

```powershell
$admin = "$env:ProgramFiles\WindowsAdminMCP\native\WindowsAdminMCP.ps1"
& $admin status
& $admin start
& $admin doctor
& $admin stop
```

Stop disconnects the interactive tunnel but does not stop the durable system service. For deliberate offline maintenance use an independent local console. The canonical updater drains work itself after package verification; callers do not need to clear the queue manually. The old root PowerShell MCP and v0.7 installer/launch path are retired; do not run old copies left outside the native package. The source root installer forwards to installer/Install-Native.ps1. Credential configuration is local-only and one-time; existing protected DPAPI credentials are reused for updates.

### Additional independent OpenAI Tunnel profiles (#56 P0-G)

In the **same elevated interactive local PowerShell** session, keep the existing primary tunnel and add a distinct second tunnel ID with its own runtime key (never paste the key into command arguments):

```powershell
& $admin list-tunnels
& $admin add-tunnel -ProfileId second -TunnelId tunnel_0123456789abcdef0123456789abcdef
& $admin list-tunnels
& $admin configure-tunnel -ProfileId second  # Rotate its runtime key without affecting primary
& $admin disable-tunnel -ProfileId second
& $admin enable-tunnel -ProfileId second
# Deliberate permanent removal, with an interactive confirmation:
& $admin remove-tunnel -ProfileId second
```

Replace the example tunnel ID with the **actual newly created, distinct OpenAI Tunnel ID** and enter its separately issued runtime key only in the encrypted local prompt. The original primary DPAPI credential remains compatible and stays on `127.0.0.1:8080`; new profiles use their own protected DPAPI files under ProgramData and distinct loopback health ports. The single existing supervisor notices additions, disables and removals without restarting healthy peers. A 401/403 blocks **only that profile** until its credentials change or it is explicitly re-enabled; a vendor crash is restarted for that profile. `status` reports each profile and vendor PID. Both ChatGPT connectors must be individually configured to their corresponding tunnel IDs; local readiness is **not** proof that both externally deliver the same MCP catalog. Do not start two active clients with the **same** tunnel ID.

## Install, update, trial and rollback

### Agent workflow (new installed version)

- `powershell_status` identifies SCM, the USER worker and the current context. `powershell_exec` is for one short command; `powershell_job` provides durable steps, logs, cancellation, resource serialization and reconciliation. Never resubmit an unknown effect automatically.
- `windows.list_windows` returns HWND/PID/start/session identities. Inspect a specific window using `windows.inspect_window(scope=WINDOW, expected_profile=...)`, then act on its fresh element reference. Native Chrome toolbar labels may contain extra delimited account details; ambiguous profile matches are rejected. UI Automation needs no CDP. `TOGGLE` uses the actual `TogglePattern` on checkboxes or toggle buttons, regardless of their reported control role.
- For a delayed UI effect, supply `expected_kind=PROCESS_STARTED` and `expected_name=camoufox`, or `expected_kind=WINDOW_CREATED` and the exact new window title, plus `expected_change=APPEARS`. `observation_timeout_ms` is 100–15000 (default 8000). The worker observes a **new identity** after a single dispatch. For `SELECT`, it also observes the element's selected state. Read `observation_state` and the original `audit_id`; `UNKNOWN` or `NOT_OBSERVED` never authorizes automatic repeat.
- `powershell_update(action=REQUEST)` creates an independent on-demand Scheduler operator in the existing elevated USER session. Save the returned `operation_id`; the connection may drop. After reconnect, use `powershell_update(action=STATUS)`, `powershell_status`, then `doctor` to check the exact installed commit, trial readiness and retained rollback. Do not request a second update while the first outcome remains unknown. No second permanent service or Job Object workaround is involved.
- After independently verifying the published MCP catalog on the **exact installed commit**, use `powershell_update(action=ACCEPT, expected_commit="<40-character installed SHA>", remote_acceptance_confirmed=true)` to request final acceptance through that same verified Scheduler operator. The explicit confirmation, elevated USER frontend, installed package integrity, exact commit, live service/USER readiness, pending rollback journal and Scheduler task principal/arguments are all checked. Read the durable result with `powershell_update(action=STATUS)` and verify `operation_action=ACCEPT`, `status=COMPLETED`, `stage=accepted`, the same commit and `rollback_pending=false`. An acceptance request with uncertain outcome must not be blindly retried. The original local-console acceptance guard remains intact; no separate privilege path or extra MCP tool is introduced.
- The previous installed release does not yet contain this MCP update entry point. Its first upgrade to this version still uses the documented independent operator; later upgrades are autonomous.

For an existing installation **that contains the updater helpers** (included in native packages from this change onward), the standard command from **any PowerShell directory**, using an interactive elevated PowerShell 7 console, is:

```powershell
& "$env:ProgramFiles\WindowsAdminMCP\native\WindowsAdminMCP.ps1" -Action update
```

The installed operator checks its own manifest-verified updater scripts, then verifies the exact main commit and matching successful CI and downloads and verifies the official package. **Only after package verification**, it stops the tunnel ingress, closes its same-session disposable `WindowsAdminMCP.exe stdio` frontends, atomically blocks new job admission and requests cancellation of queued/running jobs through the service's audited native API. The updater waits up to 60 seconds for the queue to become idle, then replaces files offline, configures **Automatic SCM service startup and an enabled interactive logon tunnel task even for the unaccepted trial**, and starts the service and trial tunnel. External acceptance remains separate: the `.rollback` journal is retained until live MCP evidence is confirmed. Uncertain effects are retained durably as `NEEDS_RECONCILIATION`, never replayed or silently marked successful. A verified candidate binary uses the legacy typed list/cancel API on the first upgrade from an old service without the atomic gate; this happens only after ingress is closed, and the idle readback must still pass. If a verified direct launcher keeps recreating blocked frontends, the updater also closes that launcher (including Codex or PowerShell if necessary). It never stops the console running the update, foreign user sessions, protected Windows processes or the independent INTERNET dataplane. Unconfirmed process identity or ownership, foreign-session clients, repeatedly reappearing frontends or an unresponsive queue stop the update safely. A pre-swap failure resumes admission and restores transport where possible. No local Git checkout, directory lookup or Git command is needed after the one-time transition. The native tunnel host itself checks `internet-tun` Up and exactly one `C:\internet\sing-box.exe`, waits for TUN if absent, and automatically starts the vendor tunnel only when ready. The result reports `TRIAL_LOCAL_READY`, `TRIAL_WAITING_FOR_TUN`, or `TRIAL_NOT_READY`, with the TUN state, `startup_ready` readback and counts of closed local clients, launchers and cancelled jobs. It intentionally does **not** accept the candidate remotely; exercise all sixteen MCP tools before explicit acceptance.

The artifact acquisition phase shows downloaded bytes every five seconds, allows up to 240 seconds overall, and retries a stalled connection after 15 seconds without incoming data. A verified `HTTP 206` response resumes at the exact retained byte offset; a wrong range or artifact length is rejected. Partial bytes survive retries within the same acquisition only and are removed on final failure. It extracts only the named package and SHA-256 receipt from GitHub's outer artifact ZIP. The package SHA-256 is still verified before maintenance, and download errors do not stop the running service or tunnel.

**One-time transition from an older installed package** that lacks `native\installer\Update-Native.ps1`: run the following single command in the same independent elevated PowerShell 7 console. It fetches a fresh, clean `main` into a unique temporary directory automatically; no knowledge of existing Git checkouts is required. Git and GitHub CLI are required for this one-time route, and the temporary checkout is retained for recovery if the trial needs rollback.

```powershell
& { $p=Join-Path $env:TEMP ('WindowsAdminMCP-bootstrap-'+[guid]::NewGuid().ToString('N')); git clone --quiet --depth 1 --branch main https://github.com/iamaman11/powershell-admin-mcp.git $p; if($LASTEXITCODE -ne 0){throw 'BOOTSTRAP_CLONE_FAILED'}; & (Join-Path $p 'WindowsAdminMCP.ps1') -Action update }
```

After that, use only the normal installed command above. A rollback to a legacy package without updater helpers must use a trusted checkout: the installed updater refuses that rollback **before** stopping the service.

If an older installed updater still reports `UPDATE_ACTIVE_JOBS`, its script cannot retroactively acquire this fix because the protected installed helper is manifest-pinned. Run the one-time trusted `main` bootstrap command above after the new version has passed CI; the new verified candidate CLI drains the old service through its existing typed job API. Once installed, the normal `-Action update` command handles busy queues automatically. No manual job cancellation, extra Chrome profile, extension or CDP setup is required.

Likewise, an installed updater reporting `UPDATE_ARTIFACT_DOWNLOAD_FAILED` cannot acquire a newer resumable downloader without that one-time trusted `main` bootstrap. The verified newer updater resumes interrupted GitHub artifact transfers by exact HTTP byte ranges, then still verifies the full CI package SHA-256 before modifying the installed service.

Manual initial-install and recovery entry points remain available. Use the CI package ZIP and its published SHA-256 from the exact accepted commit, not source-script installation. From a trusted checkout:

```powershell
.\Install-WindowsAdminMCP.ps1 -Action Verify -PackagePath <zip> -ExpectedSha256 <sha256>
.\Install-WindowsAdminMCP.ps1 -Action Install -PackagePath <zip> -ExpectedSha256 <sha256>
.\Install-WindowsAdminMCP.ps1 -Action Prepare -ExpectedCommit <commit>
```

For an existing install, use the independent local console to stop the tunnel and service intentionally and run `Maintenance -ExpectedCommit <installed-commit>` before file replacement. Close existing local stdio clients after finishing their jobs; an idle frontend can hold native DLLs and blocks replacement with `ACTIVE_FRONTEND_MAINTENANCE_REQUIRED`. The installer never kills clients. Prepare enables the existing interactive logon task and Automatic SCM service startup **before** remote acceptance, and configures SCM recovery: restart after 5/15/60 seconds, then stop retrying, with a 24-hour failure-count reset and non-crash failure handling. The host waits for TUN restoration while it is running; no Task Scheduler trigger is added for TUN changes. It never reboots Windows or runs a recovery command. Native recovery readback is included in startup readiness; configuring non-crash handling does not prove its behavior before a future Windows restart. Start via the native operator; verify all sixteen tools externally, refresh the existing connector catalog, check actual service and vendor, then run `Accept -ExpectedCommit <commit> -RemoteAcceptanceConfirmed` only after real client acceptance. **Accept records evidence and retires the rollback journal; it is no longer required for baseline autostart.** The installer never performs live replacement. `Rollback` is offline only and refuses an older binary that cannot read the current store. Schema 2/3 is backed up before transactional migration to 4; **never restore stale database backups automatically**. Same-schema rollback must preserve jobs and idempotency keys.

## Tools

If physical acceptance rejects an unaccepted schema-4 candidate, use offline `Install -ReplaceUnaccepted -PackagePath <verified-zip> -ExpectedSha256 <digest>` from a trusted checkout to repair it forward. This retains its prior file backup under `.trial-backup-<candidate-commit>` and creates the normal `.rollback` journal for the superseded candidate. Offline Install does not Accept, start services, restore a database or permit a schema downgrade; Prepare later configures normal autostart for the verified replacement without falsely accepting it. A failed swap restores the prior trial journal when rollback succeeds; interrupted repairs stay offline and retain backups for explicit recovery. Finish jobs, stop the existing tunnel/service and close stdio clients first.

- powershell_status: service identity (SYSTEM), authenticated frontend identity, USER runner availability, actual assembly/MCP/.NET/store versions, pinned expected tunnel version and local timings.
- For full read-only health without another MCP tool, call `powershell_status(include_diagnostics=true)`. Its optional `diagnostics` contains typed overall `status`, individual `component/status/reason/nextAction` checks, `reconciliation_count`, current commit and local/USER readiness. Normal status calls remain fast and omit this field. `DEGRADED` (for example due to historical unresolved jobs) is health data, not a failed MCP invocation. The local `doctor` CLI intentionally keeps a nonzero exit code for degraded health.
- To compare Tunnel-side cumulative metrics with MCP-local timing (#69), call `powershell_status(include_tunnel_metrics=true)`. The optional `tunnel_metrics` snapshot reads only the official primary Tunnel Prometheus endpoint `http://127.0.0.1:8080/metrics` with a 2-second deadline, 128-KiB maximum and no proxy or redirect. Only fixed numeric counters, queue/worker occupancy and means for `tools/call` are exposed; Tunnel IDs, other labels, requests and credentials are not returned. Missing/unreachable metrics produce a typed `tunnel_metrics.status` without failing the service status. The normal call does no Tunnel HTTP work. Metrics are cumulative, **not per-request correlated**; they cannot alone locate ChatGPT-side delays or be treated as a latency SLO.
- powershell_exec: durable single step, execution timeout 1–120 s, synchronous wait capped at 90 s from entry. PENDING carries job_id; inspect it, don't resubmit with a different key.
- powershell_job: submit (1–8 steps, each timeout 1–3600 s), status by job_id or operation_key, logs (step_index **1-based**, 1..total_steps), list with state_filter/page_size (1–100)/before_seq cursor, cancel, resume, reconcile, prune.
- powershell_screenshot: PNG ImageContent; bounded region and image size. Requires authorized default physical console; never unlocks or switches sessions. Returns typed reason and local timing on failure.
- windows.file_query: native `STAT` metadata (actual file kind, size, identity/version, timestamps, Windows owner SID when available, optional whole-file SHA-256) or `LIST` of a directory with `page_size=1..100`, immutable-order cursor and typed `CHANGED_SINCE_LIST` on directory mutation. Requires an absolute Windows path; native ACLs decide access, with no fabricated path allowlist. `execution_context=USER` is the real elevated, authenticated USER frontend; `SYSTEM` uses the existing SCM service. Read-only, no PowerShell subprocess.
- windows.file_read_chunk: native byte-exact bounded reads from an absolute path (`offset>=0`, `length=1..262144`); returns base64, actual byte count, EOF, SHA-256 of **this chunk**, and a file identity/version. Supply `expected_version` from STAT or the first chunk to detect stale reads; never treat a different version as a successful continuation. Returned `REPARSE_POINT`, ACL, sharing, missing-file and change errors are typed. UTF-8, UTF-16 and binary are handled as raw bytes. No implicit USER→SYSTEM fallback or permanent worker.
- windows.file_write: one-call `WRITE_ATOMIC` (base64 up to 16 KiB with a stable `operation_id`) or binary-safe native staged upload `BEGIN` → `APPEND` (up to 262144 bytes per call) → `COMMIT`, plus `STATUS` after lost replies and `ABORT` before commit. A stable GUID-N `operation_id` binds absolute path, expected byte count (up to 64 MiB), whole-file SHA-256 and overwrite policy (`FAIL_IF_EXISTS` or `REPLACE_IF_MATCH` with previous STAT version and hash). Each chunk is checked by offset and SHA-256. Commit uses a same-directory atomic rename or Windows `ReplaceFile`, with durable `COMMITTING` intent before rename; the follow-up STATUS verifies the resulting target hash. USER uses the elevated frontend token; SYSTEM uses the existing service token and native ACLs. **The existing SYSTEM SQLite owner now records an immutable operation/actor/target hash, pre-COMMIT intent and post-dispatch receipt for both contexts**; no second SQLite connection or database is added. The destination keeps a same-volume staging file and a capped (1024/directory) recovery journal so a restarted frontend can prove the filesystem effect even when SQLite's last receipt predates a crash. The global 100,000-row metadata limit now includes these receipts. Real service-kill/power-loss acceptance is separate from CI.
- windows.manage_window: `ACTIVATE`, `RESTORE`, `MINIMIZE`, `MAXIMIZE`, `MOVE`, `RESIZE`, `CLOSE` (graceful Win32 `WM_CLOSE`, no forced process termination) on an exact HWND/process/session identity, with Win32 before/after geometry and typed verification. Native Windows foreground restrictions still apply.
- Extended `windows.invoke_element` actions: `DOUBLE_CLICK`, `RIGHT_CLICK`, `SCROLL` with `scroll_direction` and 1–10 `scroll_units`, `HOVER`, `DRAG` with screen `target_x/target_y`, and keyboard combinations via `virtual_key=1..254` plus `ctrl/alt/shift/win`. Existing `ENTER|SPACE|ESCAPE` remain compatible. A physical dispatch with uncertain effect is never replayed.
- windows.invoke_locator: one action against exactly one live UIA element selected by exact `automation_id`, `name` and/or `role`. A disposable worker searches up to 2000 nodes; zero matches return `LOCATOR_NOT_FOUND`, multiple matches return `LOCATOR_AMBIGUOUS` without executing anything. Chrome background CDP tabs still use explicit tab refs, not a general UIA locator.
- windows.list_windows: lists up to 100 titled, visible top-level windows on the authorized physical USER desktop, including covered windows. Each `window_id` binds HWND, PID, process start and session. Never changes focus.
- windows.chrome_connection: native Chrome profile discovery and user-approved CDP. `LIST` returns profile identity and open-window IDs; `REQUEST` selects the exact window and profile without activating a different foreground window by default. If Chrome is not already foreground, it returns `CONSENT_WINDOW_UNAVAILABLE` with `next_action=SHOW_CHROME_FOR_CONSENT`. Explicit `activate_window_for_consent=true` permits a foreground activation attempt for the permission prompt only; it never approves the prompt. `STATUS` reports `CONNECTED` only after the native user consent and usable WebSocket have been verified. `DISCONNECT` closes only the selected broker. No extension, silent profile switch, credentials, browser restart or bypass of consent is introduced.
- windows.inspect_window: reads a bounded UI Automation control tree without activating elements; depth 12 / 100 returned nodes by default, hard cap depth 16 / 100 returned nodes, with at most 2,000 traversed elements per call. `offset` (default 0) and `next_offset` allow bounded pages when Chrome has many tabs or the page has many controls. Optional `name_contains` (case-insensitive accessible name, 1–128 chars), typed `role_filter` (e.g. `BUTTON`, `TEXT`, `CHECK_BOX`) and `wait_ms` (0–1500, only with a filter) find and wait for dynamic controls; no match within the requested wait yields `STATE_NOT_OBSERVED`. Optional `start_path` **together with** a fresh `start_element_id` scopes inspection to a fingerprint-verified subtree. The `path` is never authority by itself. Optional `include_details=true` (max 10 nodes) returns bounds, keyboard focusability/focus and a provider-reported clickable point without changing focus. Names of password, Edit and Document fields are redacted, never searched by name, and input **values are never returned**. Each `element_id` is valid for 30 seconds. Provider access runs in a disposable 5-second worker. Pages are live snapshots, not an atomic cross-page snapshot; always use the fresh identity when acting.
- windows.capture_window: captures **only** the selected HWND with Windows Graphics Capture, including when the window is covered. Requires `window_id` and authorized USER desktop. Output is a PNG ImageContent with structured status, max width 256–1920 (default 1280), max 2 MB and 1080 pixel height. GPU access runs in a 10-second killable worker. Minimized, capture-protected, locked/remote or unsupported windows can fail explicitly. There is no silent desktop-screenshot fallback.
- windows.invoke_element: typed UIA or CDP action on a fresh element identity. **By default `input_mode=BACKGROUND_ONLY`**: only consented CDP or native UIA patterns are permitted, with no OS `SendInput`, cursor movement or forced foreground activation. `CLICK` chooses CDP for supported Chrome content or a semantic UIA action; an unsupported physical-only action returns `FOREGROUND_INPUT_DISALLOWED` with `effect_state=NO_EFFECT`. Explicit `input_mode=ALLOW_FOREGROUND_INPUT` enables the existing verified native pointer/keyboard fallback for `CLICK`, `DOUBLE_CLICK`, `RIGHT_CLICK`, `KEY_PRESS`, `TYPE_TEXT`, `HOVER`, `DRAG` and physical-only `SCROLL`. The same policy applies to `windows.invoke_locator`. A third-party UIA provider can independently change focus, so `foreground_changed` must still be observed. Effects are separately typed as `NO_EFFECT`, `EFFECT_VERIFIED` or `EFFECT_UNKNOWN`, with method, HRESULT and stage diagnostics; an uncertain result is never automatically replayed. Expected UIA/window/process postconditions support bounded independent observation.

The action result also has nullable `execution_method=UIA_PATTERN|WIN32_SENDINPUT|CHROME_CDP` to identify the mechanism that actually dispatched or attempted input. It is absent when rejected before dispatch; `execution_method` does not imply that the intended effect occurred. Use `effect_state` and observed postconditions separately; never replay an unknown effect.

For multi-profile Chrome, use `windows.chrome_connection(action=LIST)`, then select an exact open `window_id` and `expected_profile` for `REQUEST`. In the default background-only mode the request does not activate Chrome; when the browser requires its consent dialog, `SHOW_CHROME_FOR_CONSENT` indicates that a user-visible Chrome window is required. Optional `activate_window_for_consent=true` grants only the foreground activation attempt, not permission to approve the prompt. The user must approve native Chrome consent; poll `STATUS` for `CONNECTED` before a CDP action. Once connected, tab inspection and actions do not require Chrome to remain foreground.

For background Chrome content, `windows.inspect_window(scope=TABS|TAB, expected_profile=...)` verifies the native profile and exact tab identity, returning `c1` references tied to the loader, URL and window. Consented CDP actions, including `HOVER` and bounded `SCROLL`, operate within the verified target tab without moving the OS pointer or keyboard focus. CDP hover and wheel actions verify the element's viewport position and hit test before dispatch; their effects remain unknown unless an explicit postcondition is observed. The single USER-session broker retains one CDP connection across MCP frontends. For **CDP-free** use, `scope=WINDOW` returns native UIA `e1` references; semantic `INVOKE`, `SELECT`, `TOGGLE`, `EXPAND`, `COLLAPSE`, `SET_VALUE`, and supported `CLICK` run without input injection, while unsupported physical-only actions fail closed unless `ALLOW_FOREGROUND_INPUT` was explicitly provided. An HRESULT or unknown effect is returned as typed evidence and never retried automatically. Chrome debugging must be enabled and granted using Chrome's own security UI; no second browser manager or silent permission bypass is added.

The desktop/window tools reject SYSTEM, other sessions, non-default/unavailable desktop access and stale window identities. Native file tools support USER and SYSTEM because file access does not require a desktop. `windows.file_manage` provides typed native MKDIR/COPY/MOVE/DELETE with durable receipts and optional source CAS; see [quickstart](docs/QUICKSTART.md). `windows.system_query` uses native read-only process, SCM, network, Windows Event Log, registry and Task Scheduler APIs with paged, typed results under the real frontend Windows token (USER by default); it does not promise SYSTEM access or manage these resources. `kind=TCP_CONNECTIONS` reads IPv4/IPv6 socket endpoints, state and owning PID through the Windows IP Helper API; optional `pid` filters the snapshot, `page_size`/`offset` limit output, and listener rows omit meaningless remote endpoints. The dedicated `windows.tcp_connections` publishes the same native snapshot through a narrow seven-field output contract, independent of the legacy system-query enum. Pagination is read-only but not transactional if connections change between calls. Event entries contain metadata, not message bodies. Registry values are omitted by default; explicit `include_value=true` can disclose configuration to the authenticated caller and returns bounded strings/arrays or binary SHA-256. Scheduled-task results never reveal task actions/arguments. All are subject to Windows ACLs; see [quickstart](docs/QUICKSTART.md) for typed selectors. Not every Windows application implements UI Automation or permits capture; never interpret an unsupported action as a successful click. No Chrome extension or external Node.js runtime is required, and Chrome CDP is optional. CI checks the exact 22-tool inventory and an 80-KiB upper bound for the generated catalog. If a connector omits newly published tools or fields, refresh its catalog instead of bypassing typed arguments.

All commands are trusted administrative PowerShell, not sandboxed. Timeout/cancel may leave side effects. A disconnected request does not grant permission to replay. USER worker loss records unknown effect; jobs are not automatically retried.

## Unknown effects and history

Use logs to inspect the interrupted step. Original source is encrypted for new interrupted jobs; `interrupted_source_available` discloses availability without exposing text. `include_interrupted_command=true` is an explicit operator-authorized read only for the unresolved step and may reveal sensitive script text; never request it automatically. Some legacy v3 commands were already erased and cannot be recovered from the store.

Use reconcile with decision EFFECT_CONFIRMED, NO_EFFECT_CONFIRMED or UNKNOWN and concise evidence. The service stores the immutable decision, time, correlation and authenticated local caller SID; the original execution status and key remain. RECONCILED never means successful execution. Repeating an identical decision is idempotent, contradictory changes conflict. Resume cannot replay interrupted work.

Independent jobs start individual native PowerShell processes on demand, with no fixed worker count. Admission requires both free physical memory and available commit of at least max(1 GiB, 5% of installed RAM) plus 256 MiB for each running and newly admitted execution; the store remains the queue. This is a startup safety reserve, not a hard memory limit on PowerShell. Memory observations/active reservations are diagnostic estimates and not per-script hard resource limits. A named resource_key serializes active steps using that same name; '*' is globally exclusive while active and a queued exclusive step drains existing work. Reboot plans use global exclusivity. Callers must declare conflicts: arbitrary scripts cannot be analysed reliably for shared effects. Locks cover execution of a step, not an entire paused plan or unknown external effects.

The store keeps at most 10,000 detailed job histories, with a shared hard cap of 100,000 metadata rows (**jobs plus file-operation receipts**) and a 512 MiB database+WAL budget (1 MiB admission headroom). `store.storage` reports typed AVAILABLE/WARNING/FULL/READBACK_FAILED, file and WAL bytes, page/freelist metrics, tombstone count, `file_receipts`, `metadata_total` and the exact limits. Admission refuses new distinct job/file keys with STORE_FULL/STORE_UNAVAILABLE when limits cannot be proved; an existing matching operation key still resolves idempotently. Terminal job output is compacted after 30 days in batches of up to 8; after 90 days, terminal step payloads and encrypted cwd are removed from the same SQLite transaction, keeping a small permanent job/operation-key tombstone. `NEEDS_RECONCILIATION`, queued/running and waiting jobs are never automatically shortened or deleted. Cold logs return typed HISTORY_PRUNED; state and hash-based duplicate/conflict detection remain. `prune` reports separate `pruned_count` and `tombstoned_count`; no command is replayed. The finite total budget intentionally fails closed rather than silently forgetting arbitrary operation keys; true infinite admission needs an explicitly versioned idempotency horizon, not an automatic SQL DELETE. SQLite reuses freed pages and may retain a high-water file size until a verified offline compaction. audit_persisted means a stored step result or retained audit summary, never mere admission and never an independent external audit claim.

## Diagnostics and evidence

## Windows CI and release packages

One native Windows workflow (`.github/workflows/windows-acceptance.yml`) owns compilation, tests and the release ZIP. The fast `main` push builds the exact new commit **once**, checks the live Windows service and typed MCP catalog, then verifies a real offline package install and rollback. It uploads `WindowsAdminMCP-offline-package` with a commit/run/SHA-256 receipt. The `release` job only checks the uploaded bytes and receipt on Ubuntu; it neither compiles nor creates another package. The installed updater continues to require a successful **main push** run for that exact SHA.

Each non-draft PR runs the full native service, runner and offline upgrade/rollback acceptance, including the immutable historical release fixture. This expensive suite is intentionally **not repeated** on the merge commit; PR review and required status checks must prevent untested direct pushes to `main`. Weekly Sunday 03:00 UTC (or manual **Run workflow**) runs the deeper 100-second tunnel boundary, 12-second latency fixture and experimental R0 SDK/SCM probes. These remain available but are not a per-commit release gate. Draft PRs skip the expensive workflow. The unused raw candidate and R0 lock-file artifacts, together with the retired pre-native cutover/rollback scripts, are no longer part of the project.

## Acceptance boundaries

Full Windows PR CI exercises isolated service crashes, durable jobs, SQLite migration, checkpoint/reboot guards, package upgrade and compatible rollback, queue/timeout/cancel/idempotency; weekly/manual deep CI also exercises experimental SDK contracts and latency/long-timeout fixtures. The `main` push smoke intentionally does not repeat those tests. Real Windows reboot is excluded by owner instruction; forced physical power loss, live tunnel interruption, actual 24h soak, RDP/locked/logoff scenarios, real administrators, actual installed upgrade and external PNG acceptance must be separately evidenced. No green CI or local readiness response alone proves these.
